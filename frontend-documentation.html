Sanaee Delivery — the Blazor console

An operations console for the Sanaee home-services marketplace: customers post jobs, providers bid, admins shepherd the work, money moves through wallets. This document reads the SanaeeUI/ solution end-to-end — the shell, the data layer, the API bridge, the theme and all 21 pages.

Where this UI comes from

The original repository ships only the .NET backend (src/). This fork adds an entirely new solution, SanaeeUI/, and leaves the original code intact apart from one required fix (a route typo in the histories controller that otherwise crashes API startup). The UI talks to the API as-is.

The browser never calls the API directly

The Sanaee API has no CORS policy and no authentication. The WebAssembly client therefore calls its own origin (/api/**) and the server silently forwards those calls to the API, server-to-server. Same-origin means CORS never applies; there is nothing to log into.

Quick start

You need the .NET 10 SDK. The UI runs happily in Demo mode with no backend at all; for Live mode start the API first (see the backend document).

bash
# terminal 2 — the UI (demo works on its own)
dotnet build "SanaeeUI/SanaeeUI.sln"
dotnet run   --project "SanaeeUI/SanaeeUI" --launch-profile http
# → UI listens on http://localhost:5105

# for Live mode, start the API in another terminal (default SanaeeApi:BaseUrl)
dotnet run   --project "src/Presentation/API" --launch-profile http
# → API listens on http://localhost:5270
It opens in Demo mode

The app boots with the in-memory dataset so every page renders immediately. Use the Connect to API button in the top bar to flip to Live; the chip beside it shows which source is active.

Pointing at a different API

The base URL is the single key SanaeeApi:BaseUrl, present in both SanaeeUI/appsettings.json and SanaeeUI.Client/wwwroot/appsettings.json. Edit it (or override with an env var) to target another host.

Architecture

One solution, two projects

SanaeeUI.sln contains a server host and a WebAssembly client. The host references the client assembly and adds it as an additional routing assembly, so a single URL space serves both. On the first visit the page is rendered and made interactive on the server; on later visits the same components run in the browser as WebAssembly.

SanaeeUI — the host — SanaeeUI/SanaeeUI

A Microsoft.NET.Sdk.Web project. It owns MudBlazor, the reverse proxy, the shared data services, and Razor Components with both interactive render modes. It references the client project.

SanaeeUI.Client — the app — SanaeeUI/SanaeeUI.Client

A Microsoft.NET.Sdk.BlazorWebAssembly project. It holds all 21 pages, the models, the service layer and the theme. It is the majority of the code and is shared with the server at prerender time.

Expert note — one graph, two hosts

Both startup files call the same AddSanaeeUiServices(...) extension. The only difference is the base address handed to HttpClient: the server passes the API URL directly; the WASM client passes NavigationManager.BaseUri, i.e. its own origin. That single substitution is what routes WASM traffic through the proxy and server traffic straight to the API.

AppState — the Demo/Live switch

A tiny observable holding the current DataMode (defaults to Demo) and the API base URL. SetMode/ToggleMode fire a Changed event that MainLayout subscribes to — the SanaeeDataServiceRouter reads Mode on every call, so the next data request uses the newly selected backend.

csharp — AppState
public class AppState
{
    public DataMode Mode { get; private set; } = DataMode.Demo;
    public string ApiBaseUrl { get; set; } = "http://localhost:5270/";
    public event Action? Changed;

    public void SetMode(DataMode mode)
    { if (Mode == mode) return; Mode = mode; Changed?.Invoke(); }

    public void ToggleMode() => SetMode(Mode == DataMode.Demo ? DataMode.Live : DataMode.Demo);
}
Ports & config keys

The host binds http://localhost:5105 (the http profile; the https profile adds https://localhost:7105). The API base URL comes from SanaeeApi:BaseUrl in the host's appsettings.json (http://localhost:5270/); the client's wwwroot/appsettings.json mirrors it for the WASM-side configuration.

Rendering model

Every page declares @rendermode InteractiveAuto. Blazor picks the best host automatically: the first page load is prerendered on the server and made interactive over a SignalR circuit; once the WASM bundle has downloaded, subsequent navigations run fully in the browser.

Why InteractiveAuto

It gives a fast first paint (server-rendered HTML, no download wait) while moving to the client for responsiveness, and it costs nothing to opt in here because the service graph is identical on both sides.

Composition roots

The host wires MudBlazor, the proxy, the shared services and both render modes; then maps the proxy before the Blazor endpoints.

csharp — SanaeeUI/Program.cs (abridged)
var builder = WebApplication.CreateBuilder(args);

app.UseStatusCodePagesWithReExecute("/not-found", createScopeForStatusCodePages: true);

app.UseAntiforgery();

The WASM client's root is deliberately tiny — it registers the same services, then hands its own base URI to the client.

csharp — SanaeeUI.Client/Program.cs
var builder = WebAssemblyHostBuilder.CreateDefault(args);
builder.Services.AddMudServices();

await builder.Build().RunAsync();
Expert note — one registration extension

AddSanaeeUiServices registers the singleton HttpClient, DemoDataService, SanaeeApiClient, AppState and maps ISanaeeDataService → SanaeeDataServiceRouter. Keeping this in the client project is what lets both hosts share it verbatim.

Core concept

The API bridge (BFF proxy)

Because the API sends no CORS headers, a browser cannot call it directly. The host solves this by mapping /api/{**path} and forwarding each request to SanaeeApi:BaseUrl. From the browser's point of view, the API is same-origin.

csharp — SanaeeApiProxyExtensions (abridged)
private static readonly string[] Methods =
    { "GET","POST","PUT","PATCH","DELETE","HEAD","OPTIONS" };

app.MapMethods("/api/{**path}", Methods, HandleAsync);

// Forward method, headers, body and query to the API, then stream the response back.
var target = new Uri(client.BaseAddress, "api/" + path + context.Request.QueryString);
using var request = new HttpRequestMessage(new HttpMethod(context.Request.Method), target);
// ...copy headers (skip Host / Content-Length), attach body for POST/PUT/PATCH…
using var response = await client.SendAsync(request, HttpCompletionOption.ResponseHeadersRead, ct);
context.Response.StatusCode = (int)response.StatusCode;
await response.Content.CopyToAsync(context.Response.Body);
Headers are mirrored both ways

Request headers (minus Host and Content-Length) are forwarded, and both response header collections are copied back. The transfer-encoding header is stripped so Kestrel can chunk the response itself.

API down → a clean 502

If the API is not running, the proxy catches the HttpRequestException and returns 502 with a JSON body { error, detail }. The client's methods fail gracefully and surface LastError rather than throwing, so pages degrade instead of crashing.

The router — SanaeeDataServiceRouter

It holds both services plus AppState and forwards every call to whichever is active. The UI never knows which backend it is talking to.

csharp — SanaeeDataServiceRouter (the whole trick)
private ISanaeeDataService Active =>
    _state.Mode == DataMode.Live ? _api : _demo;

public Task<IReadOnlyList<OrderListItem>> GetOrdersAsync() => Active.GetOrdersAsync();
// …every method is a one-line delegation…
Expert note — registrations are singletons

The whole graph is registered as singletons. That is fine for an admin console (a shared stats cache and a global mode switch are desirable), but it means the WASM client keeps its HttpClient alive for the session's lifetime — no per-request scoping.

Core concept

Demo vs Live

Two datasets, one UI. DemoDataService serves a small, coherent in-memory world so the console is fully explorable with nothing running. SanaeeApiClient performs real HTTP against the API. AppState carries the current mode and raises a change event the shell listens to.

csharp — AppState

The top bar shows a chip (Demo data / Live API) and a button that toggles the mode. Because MainLayout subscribes to Changed, flipping the switch re-renders the shell immediately; page components re-query on their next render.

Switching to Live does not authenticate or scope anything — it simply changes which ISanaeeDataService the router forwards to. Live mode against an unseeded or down API yields empty lists and a populated LastError.

Core concept

Wire DTOs, mapping & aggregation

The API speaks in query DTOs; the UI wants flat rows. ApiDtos.cs mirrors the wire shapes; Models/Dtos.cs holds the flattened view models; small static mappers convert one to the other. JSON is camelCase with string enums, so a converter is registered and deserialization is case-insensitive.

csharp — the tolerant list reader
private static readonly JsonSerializerOptions Json = new()
{
    PropertyNameCaseInsensitive = true,
    Converters = { new JsonStringEnumConverter() }
};

private async Task<List<TApi>> GetRawListAsync<TApi>(string url)
{
    var response = await _http.GetAsync(url);
    if (!response.IsSuccessStatusCode) { LastError = $"HTTP {(int)response.StatusCode} ({url})"; return new(); }

    using var doc = JsonDocument.Parse(await response.Content.ReadAsStringAsync());
    return doc.RootElement.ValueKind switch
    {
        JsonValueKind.Array  => doc.RootElement.Deserialize<List<TApi>>(Json)!,   // bare array
        JsonValueKind.Object => /* PagedResult { items:[...] } or a single object */ …,
        _ => new List<TApi>()
    };
}

That one helper means the client is resilient to the API's three response shapes: a bare array, the PagedResult envelope ({ items: [...] }), or a single object.

Aggregation for per-entity endpoints

Several entities are only exposed per parent — offers per order, documents per provider, reviews per reviewee, messages per order, addresses/phones per user. To show them in a flat table the client fetches a page of parents and fans out in parallel, then flattens:

csharp — offers are only exposed per order
public async Task<IReadOnlyList<OfferListItem>> GetOffersAsync()
{
    var orderIds = (await GetOrdersAsync()).Select(o => o.Id).Where(id => id != 0)
                                          .Take(AggregateCap).ToList();   // AggregateCap = 20
    var dtos = await GetForParentsAsync<GetAllOffersForOrderDto>(
        orderIds, id => $"api/Offers?OrderId={id}");
    return dtos.Select(MapOffer).ToList();
}

The page-size ceiling

The API validates pageSize to a maximum of 100. The client sets PageSizeAll = 100 for its "all" reads; asking for more returns a 400 validation error. Combined with AggregateCap = 20, the console shows up to 100 rows per list and up to 20 parents' worth of aggregated rows.

Expert note — mapping quirks inherited from the API

Some mappers have to paper over API gaps: GetAllOffersForOrderDto carries no OfferId (the UI sets it to 0), and the messages DTO omits the order id, so the mapper injects the parent id it already knows. These are documented under Known quirks.

The global search term is dropped on arrival

OnSearchKeyDown builds /orders?q={term} and navigates, but Orders.razor never reads the q query parameter — it only filters on its own _search field. So the search box jumps you to Orders and then discards what you typed; you have to re-enter it in the page's own search field. Wiring it up needs NavigationManager + QueryHelpers.ParseQuery in OnInitializedAsync.

    OpenOrders  = orders.Count(o => o.Status == OrderStatus.Pending),
    InProgressOrders = orders.Count(o => o.Status == OrderStatus.InProgress),
    // …
    TotalRevenue    = payments.Where(p => p.Status == PaymentStatus.Success).Sum(p => p.Amount),
    WalletLiability = wallets.Sum(w => w.Balance),
    AverageRating   = reviews.Count == 0 ? 0 : Math.Round(reviews.Average(r => r.Rating), 2)
};
stats.OrdersByStatus = Enum.GetValues<OrderStatus>()
    .Select(s => new OrderStatusBucket { Status = s, Count = orders.Count(o => o.Status == s) }).ToList();
// …OrdersByCategory…
return stats;
A dashboard call fans out

Building the stats triggers the seven list queries above, several of which themselves aggregate over parents. In Live mode this is a burst of parallel HTTP calls — deliberately bounded by AggregateCap, but still the heaviest page in the app.

Two charts only render in Demo mode

The dashboard lays out four charts: a revenue line, a status donut, a category bar and a cancellation-reason bar. The two data sources differ by mode:

BucketDemoLive

RevenueTrend (7-day line)✓ — computed from payments by date✗ never populated

DemoData.BuildStats() fills all four; the live SanaeeApiClient.GetDashboardStatsAsync() fills only the first two (it has no per-day payment breakdown and no cancellation-reason counts to read). So in Live mode the revenue-line and reason charts render empty.

Expert note — the buckets are computed client-side

The API exposes no aggregate endpoint. Every KPI, trend and chart bucket is derived in the client from the fetched lists. That keeps the client independent of the backend's (missing) analytics but means accuracy is limited to whatever the capped page sizes returned.

Expert note — cancellation body shape

Only a free-text reason is collected, but the admin-cancel command expects (OrderId, ReasonId, Notes, IssueRefund). The client sends reasonId = 0 and puts the text in notes with issueRefund = false, so a completed order cannot be refunded through the UI. See Known quirks.

Known quirks

The console leans on an API that was never designed for a browser. These are the seams — mostly faithful, sometimes lossy.

#QuirkEffect
1Offers list DTO has no OfferIdAccept / reject / cancel offer cannot address a real id (the UI sets it to 0); actions hit the endpoint but cannot succeed.
2No aggregate/analytics endpointAll dashboard KPIs and buckets are computed client-side from capped pages.
3Per-entity-only endpointsOffers, documents, reviews, messages, addresses, phones are aggregated by iterating up to 20 parents (AggregateCap).
4pageSize capped at 100“All” reads request 100; larger asks return a 400 validation error.
5Availability toggle never sends the new valueLive SetProviderAvailabilityAsync(id, available) sends PATCH api/Providers/{id} with a null body, so available is dropped and the server has nothing to change. Demo applies it locally, which is why the switch appears to work there.
6Admin cancel needs a ReasonId, UI has free textSends reasonId: 0 with the text in notes and issueRefund: false.
7No audit-log endpointGetAuditLogsAsync returns an empty list; the Audit Logs page is structurally complete but always empty.
8No reviews list endpoint (per reviewee only)The UI omits the reviewee name and shows reviews floored to known provider/customer ids.
9No CORS, no auth on the APIWorked around with the same-origin proxy; the whole console is unauthenticated and trusted-network-only.
10Route typo blocks API startupFixed in this fork ([contorller] → [controller]); the client points at the corrected api/OrderStatusHistories/admin path.
11Broken order-history projection on the APIGET /api/OrderStatusHistories/admin returns 500 server-side; the Order Timeline page surfaces the empty/error state.
12Chat not connected to SignalRReads historical messages; sending and real-time updates are not implemented (and the backend hub is empty).
13Global search term is dropped on arrivalThe shell navigates to /orders?q=… but Orders.razor never reads q — only its own _search field filters. The typed term is discarded.
14Demo mode mutates shared stateDemoDataService writes into the static DemoData lists, so demo-created/edited rows persist across navigations — unlike Live, where each action is a fresh HTTP call.
15Two dashboard charts only populate in DemoRevenueTrend and CancellationReasons are filled by DemoData.BuildStats() but never by the live client, so those charts render empty in Live mode.
What gracefully degrades

When the API is unreachable the proxy returns 502 and the client stores it in LastError while returning empty lists — pages show EmptyState rather than throwing. Flipping back to Demo restores a fully populated console instantly.

Glossary

Blazor Web App
A single .NET project that hosts Razor components and can render them on the server, in the browser via WebAssembly, or both — chosen per component with a render mode.
Render mode
Where and how a component becomes interactive. InteractiveAuto starts on the server and hands over to WebAssembly once the bundle is available.
WebAssembly (WASM)
.NET running inside the browser sandbox. The client project compiles the UI to a WASM bundle the host serves.
Prerendering
Server-rendered HTML for the first paint so the page appears before interactivity is wired up.
BFF / reverse proxy
Backend-for-frontend: the host forwards /api/** to the real API so the browser only ever talks to its own origin (avoiding CORS).
Facade
A single interface (ISanaeeDataService) that hides whether data comes from the demo dataset or the live API.
Aggregation (N+1 fan-out)
Calling a per-parent endpoint once per parent and flattening the results, used for entities the API only exposes per order/provider/user.
Design token
A named value (colour, radius, font) held in one place. Here every colour lives in SanaeeBrand and is emitted as a CSS variable.
MudBlazor
A Material-Design component library for Blazor, supplying the theme provider, tables, dialogs, charts and shell primitives.
InteractiveAuto
The default render mode for every page here: server-first, WASM-after, one service graph for both.
