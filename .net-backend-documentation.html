Sanaee Delivery — the .NET backend

An on-demand home-services marketplace for the Egyptian market: a customer posts a job, local verified providers bid with offers, one is accepted, the job runs to completion, and money moves through an internal wallet ledger. This document reads the original src/ solution end-to-end.

The headline caveat

The backend is a well-structured domain skeleton but not production-ready: there is no authentication or authorization at all, passwords are stored in plaintext, and several services are stubs. A new client job flow works, but nothing is guarded. Read Security and Known issues before trusting anything.

Quick start

You need the .NET 10 SDK and a reachable SQL Server (a full instance or LocalDB both work). The connection string lives in appsettings.json under ConnectionStrings:DefaultConnection.

bash
cd "Sanaee Delivery"          # repo root (contains Sanaee Delivery.slnx)
dotnet build
dotnet run --project src/Presentation/API --launch-profile http
# → API listens on http://localhost:5270

# Apply the schema (migrations-first; the app does NOT auto-migrate):
dotnet ef database update --project src/Infrastructure/Persistence --startup-project src/Presentation/API
Before you can see data

The built-in seeder is commented out and stale, and there is no Swagger UI. On a fresh database the endpoints answer 200 with empty lists. Two routes must be fixed in the code first — see Known issues — one of which crashes startup, and the OrderStatusHistories projection which throws at runtime.

Using LocalDB

If no SQL Server is installed, install SQL Server LocalDB and point the connection string at Server=(localdb)\\mssqllocaldb;Database=Sanaee_Delivery;Trusted_Connection=True;TrustServerCertificate=True; — it can be supplied via the env var ConnectionStrings__DefaultConnection without touching the committed config.

Smoke-test a public read once running:

bash
curl http://localhost:5270/api/Categories
# → [{ "categoryId": 1, "name": "Plumbing", ... }]

Architecture

Four layers, one direction

Outer layers know about inner layers, never the reverse. Domain sits at the centre (concepts) and the API at the edge (HTTP); Application and Persistence sit in between as the contract and the machinery.

Domain — src/Core/Domain

Pure C# domain concepts: entities, enums, domain events and the DomainException. No EF, no HTTP.

Application — src/Core/Application

The use-case layer: one folder per feature holding Commands, Queries, DTOs, AutoMapper profiles and validators, plus cross-cutting behaviours and persistence contracts (IUnitOfWork, repositories).

Persistence — src/Infrastructure/Persistence

The EF Core implementation: the AppDbContext, per-entity configurations, interceptors, generic + specialised repositories, Unit of Work, migrations and stub infrastructure services.

API — src/Presentation/API

The HTTP edge: controllers, the composition root, the global exception handler and the SignalR hub.

Expert note — the dependency rule

Domain references nothing; Application references Domain; Persistence references Application (and therefore Domain); API references Application + Persistence. Controllers depend only on MediatR's ISender, never on concrete handlers, so the HTTP edge stays thin.

Request lifecycle

A call such as GET /api/Orders/admin?pageNumber=1&pageSize=20 travels:

  1. GlobalExceptionHandler wraps the pipeline first, so any thrown exception becomes a ProblemDetails.
  2. Routing selects the controller action via attribute routes.
  3. The controller binds the query object and calls _mediator.Send(query).
  4. ValidationBehavior runs the matching FluentValidation validator; failures throw ValidationException.
  5. The handler queries through IUnitOfWork.Repository<T>(), projects with AutoMapper, and returns a PagedResult<T>.
  6. EF Core translates LINQ to SQL Server and materialises the page.
  7. The controller returns the DTO, serialised as JSON (camelCase, enums as strings).
Expert note — why DTOs are projected

Read queries use .ProjectTo<TDto>(mapper.ConfigurationProvider) over an AsNoTracking() IQueryable, so only the DTO's columns are selected in SQL and no change tracking is allocated. This is efficient — but it is also how the OrderStatusHistories bug slipped in: the projection source type and the profile's CreateMap source type must agree.

What is missing from the pipeline

Core concept

Response shape

There is no success envelope. A controller returns the DTO directly, or a PagedResult<T> for lists. Only errors get a wrapper, and it is the standard ProblemDetails shape produced by ASP.NET Core.

json
{ "categoryId": 1, "name": "Plumbing",
  "description": "Plumbing & pipe repair", "isActive": true }
json
{ "items": [ { "orderId": 1, … } ],
  "pageNumber": 1, "pageSize": 20, "totalCount": 42, "totalPages": 3,
  "hasPreviousPage": false, "hasNextPage": true }
json
{ "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Validation Failed", "status": 400,
  "errors": { "PageSize": [ "Page size must be between 1 and 100." ] } }
Expert note — PagedResult

PagedResult<T> lives in Core.Application.Common.Models and exposes Items, PageNumber, PageSize, TotalCount, TotalPages, HasPreviousPage, HasNextPage. It is produced by a ToPagedListAsync(pageNumber, pageSize) extension over IQueryable. The default pageSize is small and every list validator caps it at 100.

Core concept

Error handling

Handlers and domain entities throw. A single GlobalExceptionHandler (an IExceptionHandler, registered in Program.cs and living in API/Exceptions/) translates each exception type to a status code and a ProblemDetails body. Controllers contain no try/catch. The switch is exhaustive-by-convention with a catch-all that never leaks internals.

ThrownHTTPTitle emittedProduced by

BadRequestException400Bad request sent!Command handlers (e.g. wrong OTP).
NotFoundException404Resource not found!Handlers when an id does not exist.
ConflictException409Conflict!State conflicts.
InvalidOperationException500Invalid Operation!Misuse of a service/operation.
DomainException406Domain Exception! Entity invariants — every Order.AcceptOffer/StartWork/Complete/Cancel* guard. Note the status: 406 Not Acceptable, not 400.

json — a domain rule firing

  "detail": "You must accept offer for this order first." }
406 for a business-rule violation is unusual

DomainException is the workhorse of the whole state machine, yet it surfaces as 406 Not Acceptable — a content-negotiation status. Clients that branch on 400/409 for “invalid state” will miss every guard on Order. InvalidOperationException is also mapped to 500, which turns recoverable misuse into server errors.

Core concept

Validation

Every command/query has a FluentValidation validator, discovered by assembly scan in AddApplicationServices() and executed automatically by a MediatR pipeline behaviour before the handler runs.

csharp — ValidationBehavior (abridged)
public class ValidationBehavior<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
{
    public async Task<TResponse> Handle(TRequest request,
        RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        foreach (var v in validators)
        {
            var result = await v.ValidateAsync(request, ct);
            if (!result.IsValid)
                throw new ValidationException(result.Errors);
        }
        return await next();
    }
}
Two validators validate the wrong type

GetProviderCategoryByIdQueryValidator validates a DTO instead of the query, and GetDefaultAddressQueryValidator validates GetUserAddressesQuery. Those queries therefore run unvalidated. See Known issues.

The order state machine

csharp — Order (the interesting parts)
public void AcceptOffer(int offerId)
{
    if (Status != OrderStatus.Pending)
        throw new DomainException("You can not accept offers for this order.");
    Status = OrderStatus.OfferAccepted;
}

public void StartWork()
{
    if (Status != OrderStatus.OfferAccepted)
        throw new DomainException("You must accept offer for this order first.");
    Status = OrderStatus.InProgress;
}

public void Complete()
{
    if (Status != OrderStatus.InProgress)
        throw new DomainException("You must start this order first.");
    Status = OrderStatus.Completed;
}

public void CancelByAdmin(int ReasonId, bool IssueRefund)
{
    if (Status == OrderStatus.Cancelled) throw new DomainException("Order is already cancelled !");
    if (Status == OrderStatus.Completed && !IssueRefund)
        throw new DomainException("Yos must define the refund issue first !");
    Status = OrderStatus.Cancelled;
    AddDomainEvent(new OrderCancelledByAdminEvent(Id, UserId, Offer?.ProviderId, ReasonId, IssueRefund));
}

Category mapping will null-ref on root categories

CategoryMappingProfile maps GetCategoryDto.ParentCategoryName with opt.MapFrom(src => src.ParentCategory!.Name). The null-forgiving operator ! lies: every top-level category has a null parent, so projecting one throws. It needs a conditional map (or src.ParentCategory?.Name).

Provider onboarding / KYC

Four entities form the trust trail for getting a provider live. Each history table records Status, optional Notes, a ChangedAt timestamp and a ChangedBy admin id:

  • ApplicationHistory — the application decision trail (ApplicationStatus: Pending · Approved · Rejected · ActionRequired).
  • ProviderStatusHistory — the account status trail (ProviderStatus: Active · Suspended · Inactive).
  • ProviderDocument — a submitted KYC artefact (DocumentType: NationalId · CriminalRecord · WorkPermit · PersonalPhoto) with a DocumentStatus (Pending · Approved · Rejected · Expired · ReUploadRequired), a DocumentUrl and an optional ChangedBy.
  • ProviderCategory — the skills that let a provider receive matching orders.

Admin actions on documents and statuses flow through the ProviderDocuments and ProviderStatusHistories features, which write these tables; the frontend exposes them as the Applications, Provider Status and Provider Documents pages.

Core concept

Domain events

Entities raise events through AddDomainEvent; a persistence interceptor collects them on SaveChanges and republishes them through MediatR, where handlers react (e.g. notify the other party, reopen competing offers).

EventRaised byIntent
OfferCreatedEventOffer.Create()Notify the customer of a new bid.
OfferAcceptedEventOffer.Accept()Close the bidding, inform the winner.
MessageSentDomainEventMessage.Create*Fan out over SignalR (ChatHub).
OrderCancelledByCustomerEventOrder.CancelByCustomerNotify provider.
OrderCancelledByProviderEventOrder.CancelByProviderReopen other offers.
OrderCancelledByAdminEventOrder.CancelByAdminRefund handling.
Events are raised but not delivered

Because the soft-delete interceptor replaced the domain-event interceptor during registration (see Interceptors), and because NotificationService is a stub, domain events do not currently reach any real consumer. The wiring exists; the plumbing is inert.

How an event travels

Events are plain records implementing an empty IDomainEvent marker. On SaveChanges the dispatch interceptor wraps each one in a DomainEventNotification<TEvent> (a MediatR INotification) and publishes it, so every INotificationHandler<DomainEventNotification<TEvent>> runs — often several per event, in parallel fan-out. Handlers split cleanly into notify (push via INotificationService), side-effect (refund via IPaymentService, fine via IProviderPenaltyService) and audit (write an AuditLog row through the unit of work).

EventSignatureHandlers (feature folder)
OfferCreatedEvent(Offer Offer, int UserId, int ProviderId) NotifyCustomerOnOfferCreated → push “offer created” to the customer.
OfferAcceptedEvent(int OfferId, int OrderId, int UserId, int ProviderId) NotifyProviderOnOfferAccepted → push “offer accepted” to the winning provider.
MessageSentDomainEvent(Message Message) none registered — intended to fan out over SignalR.
OrderCancelledByCustomerEvent(int OrderId, int UserId, int? ProviderId, int ReasonId) NotifyProviderOnCustomerCancellation (push) · ProcessCustomerRefund → ProcessCustomerCancellationRefundAsync.
OrderCancelledByProviderEvent(int OrderId, int UserId, int ProviderId, int ReasonId) NotifyCustomerOnProviderCancellation (apology push) · ApplyProviderPenalty → ApplyPenaltyForCancellationAsync.
OrderCancelledByAdminEvent(int OrderID, int UserId, int? ProviderId, int ReasonId, bool IssueRefund) NotifyBothParties (push customer + provider) · RefundPayment (if IssueRefund) · AuditLogHandler (inserts an AuditLog with the reason text).
Why three handlers for one admin cancel

An admin cancellation is the only action with a legal, financial and audit dimension, so it fans out to three independent handlers. Each is a single responsibility that can later be swapped (e.g. a real payment gateway) without touching the Order entity — the entity only records intent and raises the event.

Inconsistent namespaces and casing

Two event records live in a bare Domain.Events namespace instead of Core.Domain.Events (OfferCreatedEvent, OrderCancelledByAdminEvent), and the admin event names its first parameter OrderID while the others use OrderId. Cosmetic, but it forces extra using statements and trips up anyone refactoring by pattern.

Core concept

Security

There is no authentication or authorization

A repo-wide search finds no AddAuthentication, no JWT/cookie package, and no [Authorize] attribute. UseAuthorization() runs with no scheme, so every endpoint is effectively public. Admin-only routes are “admin” in name only.

  • Passwords are stored and compared as plaintext in CreateCustomerCommandHandler, CreateProviderCommandHandler and ChangePasswordCommandHandler — no hashing.
  • Phone OTP is generated and cached in memory, then written to the application log (there is no SMS integration). See Phone OTP.
  • There is no CORS policy, so browser clients rely on a same-origin proxy or are blocked.
  • ICurrentUserService is declared but never implemented or registered — there is no notion of “the current user” server-side.
Expert note — what “admin” means here

Many endpoints take an AdminId in the route or body (e.g. POST /api/ApplicationHistories/{AdminId}). Nothing verifies that the caller is that admin; the id is trusted verbatim. Treat the whole surface as trusted-network-only.

csharp — controller + handler pattern
[HttpPatch("accept/{OfferId}")]
public async Task<ActionResult> AcceptOffer(int OfferId)
    => Ok(await _mediator.Send(new AcceptOfferCommand(OfferId)));

// --- handler ---
public sealed class AcceptOfferCommandHandler(IUnitOfWork uow)
    : IRequestHandler<AcceptOfferCommand, Unit>
{
    public async Task<Unit> Handle(AcceptOfferCommand req, CancellationToken ct)
    {
        var offer = await uow.Repository<Offer>().GetByIdAsync(req.OfferId, ct)
            ?? throw new NotFoundException(nameof(Offer), req.OfferId);
        offer.Accept();                         // domain method raises an event
        await uow.SaveChangesAsync(ct);
        return Unit.Value;
    }
}
Expert note — one behaviour only

Only ValidationBehavior is registered. A LoggingBehavior exists but is internal and never wired, and there is no transaction behaviour — each handler is responsible for its own SaveChangesAsync.

Pattern

Repository & Unit of Work

Handlers depend on IUnitOfWork (in Application.Common.Contracts.Persistence). It exposes a generic Repository<T>() plus three specialised repositories (Address, UserPhone, Wallet) and a single SaveChangesAsync that commits all tracked changes atomically.

csharp — the read pattern
var page = await uow.Repository<Order>()
    .GetQueryable()
    .AsNoTracking()
    .OrderByDescending(o => o.Id)
    .ProjectTo<GetAllOrdersForAdminDto>(mapper.ConfigurationProvider)
    .ToPagedListAsync(query.PageNumber, query.PageSize, ct);
Blanket filters disabled

Several list handlers call .IgnoreQueryFilters(), which bypasses EF's soft-delete global filters and can return soft-deleted rows. It is convenient, but a maintenance trap.

csharp — the contract
public interface IUnitOfWork : IDisposable
{
    IAddressRepository    AddressRepository  { get; }
    IUserPhoneRepository  UserPhoneRepository{ get; }
    IWalletRepository     WalletRepository   { get; }
    IBaseRepository<TEntity> Repository<TEntity>() where TEntity : class;
    Task<int> CompleteAsync(CancellationToken cts);
}

Note the interface mixes typed repositories (for the three aggregates with bespoke queries) with a generic Repository<T>() for everything else, and its members are named CompleteAsync while most handlers call SaveChangesAsync — both exist depending on the handler.

Paging helpers

Paging is a hand-rolled extension rather than a library. PaginationExtensions.ToPagedListAsync<T> counts the source, then Skip((pageNumber-1)*pageSize).Take(pageSize), and wraps the result in a PagedResult<T> that computes TotalPages, HasPreviousPage and HasNextPage on the fly.

csharp — PagedResult<T>
public class PagedResult<T>
{
    public IReadOnlyList<T> Items { get; }
    public int PageNumber { get; }
    public int PageSize   { get; }
    public int TotalCount { get; }
    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);
    public bool HasPreviousPage => PageNumber > 1;
    public bool HasNextPage     => PageNumber < TotalPages;
}

Infrastructure stubs

Three application contracts are satisfied by no-op implementations in Infrastructure/Persistence/Services/. Every method is await Task.CompletedTask — the seams exist so a real provider (SMS, payment gateway, penalty engine) can be dropped in without touching the domain.

ChatHub is empty and MessageSentDomainEvent has no handler

API/Hubs/ChatHub.cs is a bare class ChatHub : Hub { } with no methods, and MessageSentDomainEvent has no INotificationHandler registered. Messaging is therefore persisted but never pushed in real time — the frontend chat composer is UI-only to match.

Core concept

Interceptors

Two EF Core interceptors exist:

  • SoftDeleteInterceptor — rewrites Delete into IsDeleted = true for ISoftDeletable entities.
  • DispatchDomainEventsInterceptor — after save, collects each entity's domain events and publishes them through MediatR.
Only the second one is effective

AddInfrastructureServices() registers AddDbContext<AppDbContext> twice: the first call attaches the soft-delete interceptor, the second (with the domain-events interceptor) becomes the effective registration. The soft-delete interceptor therefore never runs — deletes are hard deletes, and soft-delete query filters have nothing to hide.

Order lifecycle

A job moves through five states driven by explicit domain methods, each guarding the previous state:

Expert note — cancellation rules differ per actor

A customer may not cancel a completed or in-progress order; a provider may cancel only an accepted or in-progress order; an admin may cancel anything but a completed order requires an explicit IssueRefund flag. All three raise a distinct cancellation event carrying the reason id.

Deep dive

Offers & bidding

Providers bid on a pending order with a labour cost, optional material cost and an arrival time. An offer is created through its factory and accepted/rejected/cancelled through domain methods that raise events.

csharp — Offer.Create
var offer = Offer.Create(order, providerId, laborCost, materialCost, notes, arrivalTime);
offer.AddDomainEvent(new OfferCreatedEvent(offer, order.UserId, providerId));
The offer list DTO has no id

GetAllOffersForOrderDto omits the offer id, so a client that lists offers cannot then address one to accept/reject/cancel it without a separate lookup. The bundled Blazor client works around this by setting the id to 0.

Deep dive

Wallet & payments

Every user has a wallet. Money changes through guarded domain methods so the balance can never silently go wrong, and each change is mirrored by an immutable WalletTransaction row.

csharp — Wallet + Payment
public void Deposit(decimal amount)
{
    if (amount <= 0) throw new InvalidOperationException("Amount must be greater than 0.");
    if (!IsActive)  throw new InvalidOperationException("Wallet is freezeing now.");
    Balance += amount; UpdatedAt = DateTime.UtcNow;
}

public void Withdraw(decimal amount)
{
    if (amount <= 0) throw new InvalidOperationException("Amount must be greater than 0.");
    if (!IsActive)  throw new InvalidOperationException("Wallet is freezeing now.");
    if (Balance < amount) throw new InvalidOperationException("Your balance does not enough …");
    Balance -= amount; UpdatedAt = DateTime.UtcNow;
}

// Payment: starts Pending, then a state machine of its own
new Payment(amount, method, type, userId, orderId).MarkAsSuccess("TXN-0001");

Deep dive

Phone OTP verification

Phone numbers are verified by a one-time code. The code is generated server-side, cached in memory for ten minutes, and — for development — written to the log. There is no SMS provider wired up.

csharp — SendphoneOtpCommandHandler (abridged)
var code = Random.Shared.Next(100000, 999999).ToString();
_cache.Set($"OTP:{phoneNumber}", code, TimeSpan.FromMinutes(10));
_logger.LogInformation("OTP for {Phone} is {Code}", phoneNumber, code);   // ⚠ logged
return "Code sent Successfully";
Verification is never persisted

In VerifyPhoneOtpCommandHandler the IsVerified / IsPrimary assignments are commented out, so a “verified” phone is not marked verified in the database. Because the cache is in-process, codes also vanish on restart and are not shared across instances.

Glossary

Clean Architecture
A way of arranging code so that business rules sit at the centre and frameworks (web, database) sit at the edges, with dependencies pointing inward.
CQRS
Command-Query Responsibility Segregation — separating “do something” requests (commands) from “read something” requests (queries). Here both are MediatR messages.
MediatR
A small in-process mediator. A controller sends a message and a matching handler runs; the controller never references the handler type.
DTO
Data Transfer Object — a plain shape used on the wire, kept separate from the database entity.
DbContext
EF Core's gateway to the database, exposing DbSet<T> collections queried with LINQ.
Migration
A versioned, code-generated change to the database schema.
Interceptor
A hook into EF Core's save pipeline — used here to soft-delete and to dispatch domain events.
Domain event
A record that “something happened” in the domain (e.g. OfferAcceptedEvent), published so other parts of the system can react.
PagedResult<T>
The standard paged-list wrapper: items plus page metadata.
ProblemDetails
An RFC-7807 JSON shape (title, status, detail, errors) used for errors.
Unit of Work
An object that tracks changes across repositories and commits them together in one transaction.
